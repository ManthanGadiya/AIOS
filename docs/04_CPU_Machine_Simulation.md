# AIOS: An AI-Powered Multiprogramming Operating System Simulator

# 4. CPU / Machine Simulation

## 1. Purpose

This document defines the simulated CPU and machine architecture used by AIOS.

The purpose of the CPU / Machine Simulation is to provide a controlled hardware environment on which the operating system can execute processes and demonstrate:

* Instruction execution
* CPU registers
* Memory access
* Program execution
* System calls
* Interrupt generation
* Context switching
* Process termination
* Error conditions

The simulator does not interact with the physical CPU of the host computer. The C++ program acts as a virtual machine that imitates the behaviour required by the AIOS operating system.

---

# 2. Simulated Machine Overview

The simulated machine consists of:

```text
Simulated Machine
│
├── CPU
│   ├── PC
│   ├── IR
│   ├── ACC
│   ├── MAR
│   ├── MBR
│   └── FLAGS
│
├── Main Memory
│
├── Instruction Set
│
├── Program Execution Unit
│
└── Interrupt Interface
```

The CPU communicates with the OS through well-defined interfaces.

---

# 3. CPU Architecture

The simulated CPU contains the following registers:

```text
CPU
│
├── PC      Program Counter
├── IR      Instruction Register
├── ACC     Accumulator
├── MAR     Memory Address Register
├── MBR     Memory Buffer Register
└── FLAGS   Status Flags
```

---

# 4. Program Counter (PC)

The Program Counter stores the address of the next instruction to be executed.

Example:

```text
PC = 105
```

means that the next instruction will be fetched from simulated memory location `105`.

Normally:

```text
PC → next instruction
```

After fetching an instruction:

```text
PC = PC + instruction_size
```

Branch instructions may modify the PC directly.

---

# 5. Instruction Register (IR)

The Instruction Register stores the instruction currently being executed.

Example:

```text
IR = ADD R1
```

The CPU uses the IR during the decode and execute stages.

---

# 6. Accumulator (ACC)

The Accumulator stores intermediate arithmetic or logical results.

Example:

```text
LOAD 10
ADD 5
```

Execution:

```text
ACC = 10

ACC = ACC + 5

ACC = 15
```

The ACC provides a simple mechanism for demonstrating CPU computation.

---

# 7. Memory Address Register (MAR)

The MAR stores the memory address that the CPU wants to access.

Example:

```text
MAR = 200
```

This means the CPU is requesting access to memory location `200`.

---

# 8. Memory Buffer Register (MBR)

The MBR temporarily stores data being transferred between the CPU and simulated memory.

For a read:

```text
Memory
   ↓
MBR
   ↓
CPU
```

For a write:

```text
CPU
   ↓
MBR
   ↓
Memory
```

---

# 9. FLAGS Register

The FLAGS register stores status information generated by CPU operations.

Initial flags may include:

```text
FLAGS
├── ZERO
├── NEGATIVE
├── CARRY
├── OVERFLOW
└── ERROR
```

Not every instruction needs to modify every flag.

For example:

```text
ADD 5
```

may update:

```text
ZERO
NEGATIVE
CARRY
OVERFLOW
```

These flags can later be used by conditional instructions.

---

# 10. Instruction Format

AIOS will use a simple instruction representation.

Conceptually:

```text
OPCODE OPERAND
```

Examples:

```text
LOAD 10
STORE 20
ADD 5
JMP 100
JZ 150
SYSCALL 1
HALT
```

The instruction format is intentionally simple so that the focus remains on operating system behaviour.

---

# 11. Instruction Set

The initial instruction set is:

| Instruction | Purpose                           |
| ----------- | --------------------------------- |
| `LOAD`      | Load a value from memory into ACC |
| `STORE`     | Store ACC into memory             |
| `ADD`       | Add a value to ACC                |
| `SUB`       | Subtract a value from ACC         |
| `MUL`       | Multiply ACC by a value           |
| `DIV`       | Divide ACC by a value             |
| `JMP`       | Unconditional jump                |
| `JZ`        | Jump if ZERO flag is set          |
| `READ`      | Request simulated input           |
| `WRITE`     | Request simulated output          |
| `SYSCALL`   | Request an OS service             |
| `HALT`      | Terminate the current program     |

The instruction set may be extended if a later OS component requires an additional instruction.

# 12. Instruction Categories

The instructions can be divided into four categories.

## 12.1 Data Instructions

```text
LOAD
STORE
```

Used for memory operations.

## 12.2 Arithmetic Instructions

```text
ADD
SUB
MUL
DIV
```

Used for computation.

## 12.3 Control Flow Instructions

```text
JMP
JZ
HALT
```

Used to control program execution.

## 12.4 OS / I/O Instructions

```text
READ

SYSCALL
```

Used to request operating system services.

# 13. Fetch-Decode-Execute Cycle

The CPU executes instructions using the standard:

```text
FETCH → DECODE → EXECUTE
```

cycle.

Detailed flow:

```text
             ┌─────────────┐
             │     PC      │
             └──────┬──────┘
                    │
                    ▼
             Fetch Instruction
                    │
                    ▼
             Store in IR
                    │
                    ▼
                 Decode
                    │
                    ▼
                 Execute
                    │
                    ▼
          Update Registers / Flags
                    │
                    ▼
              Update PC
                    │
                    ▼
             Next Instruction
```

---

# 14. Fetch Phase

During the fetch phase:

1. The PC identifies the next instruction.
2. The address is placed in the MAR.
3. Memory is accessed.
4. The instruction is loaded into the MBR.
5. The instruction is copied into the IR.
6. The PC is advanced.

Conceptually:

```text
PC
 ↓
MAR
 ↓
Memory
 ↓
MBR
 ↓
IR
```

---

# 15. Decode Phase

The CPU examines the instruction stored in the IR.

Example:

```text
IR = ADD 5
```

The CPU identifies:

```text
Opcode  = ADD
Operand = 5
```

The instruction is then passed to the appropriate execution logic.

---

# 16. Execute Phase

The CPU performs the operation specified by the instruction.

Example:

```text
ACC = 10

Instruction:
ADD 5

Result:
ACC = 15
```

After execution, relevant flags are updated.

---

# 17. Example Program

A simple simulated program:

```text
LOAD 10
ADD 5
STORE 20
WRITE 20
HALT
```

Execution:

```text
LOAD 10
   ↓
ACC = 10

ADD 5
   ↓
ACC = 15

STORE 20
   ↓
Memory[20] = 15

WRITE 20
   ↓
Output = 15

HALT
   ↓
Process Terminated
```

---

# 18. CPU and Process Relationship

The CPU does not permanently belong to one process.

The Scheduler determines which process receives the CPU.

Example:

```text
Ready Queue

P1
P2
P3

     ↓

Scheduler

     ↓

CPU

     ↓

P1 executes
```

When a scheduling event occurs:

```text
P1 Running
     ↓
Context Switch
     ↓
P2 Running
```

The CPU registers must therefore be associated with the currently running process.

---

# 19. CPU Context

The execution context of a process contains information required to resume execution.

At minimum:

```text
Process Context
├── PC
├── IR
├── ACC
├── MAR
├── MBR
└── FLAGS
```

During a context switch:

```text
Running Process
      │
      ▼
Save CPU Context → PCB
      │
      ▼
Scheduler selects next process
      │
      ▼
Load CPU Context ← PCB
      │
      ▼
New Process Running
```

This provides the foundation for multiprogramming.

---

# 20. CPU and Memory Interaction

The CPU accesses memory through the Memory Manager.

Conceptually:

```text
CPU
 │
 │ Logical Address
 ▼
Memory Manager
 │
 ▼
Page Table
 │
 ▼
Physical Frame
 │
 ▼
RAM
```

The CPU itself should not directly implement paging logic.

The Memory Manager is responsible for address translation and page management.

---

# 21. Logical Address

A process operates using a logical address.

For a paged memory system:

```text
Logical Address
      │
      ├── Page Number
      │
      └── Offset
```

The Memory Manager translates this into a physical address.

```text
Page Number
     │
     ▼
Page Table
     │
     ▼
Frame Number
     │
     └──────┐
            ▼
       Physical Address
```

Detailed address translation is defined in `07_Paging_Virtual_Memory.md`.

# 22. CPU and Interrupts

The CPU can encounter events that require OS intervention.

Examples:

```text
SYSCALL
Page Fault
Timer Event
Invalid Instruction
Divide by Zero
I/O Event
```

The general flow is:

```text
CPU
 │
 ▼
Event Detected
 │
 ▼
Interrupt Generated
 │
 ▼
Interrupt Manager
 │
 ▼
Interrupt Service Routine
 │
 ▼
Resume / Block / Terminate / Reschedule
```

Detailed interrupt behaviour is defined in `05_System_Calls_Interrupts.md`.

# 23. System Call Instruction

The `SYSCALL` instruction allows a process to request a service from the operating system.

Example:

```text
SYSCALL 1
```

Conceptually:

```text
Process
   │
   │ SYSCALL 1
   ▼
CPU
   │
   ▼
Interrupt
   │
   ▼
OS
   │
   ▼
System Call Service
```

Possible service identifiers may represent:

```text
1 → READ
2 → WRITE
3 → MEMORY_REQUEST
4 → PROCESS_EXIT
5 → IPC_REQUEST
```

The exact system call table will be defined in the System Calls document.

---

# 24. Error Conditions

The CPU shall detect basic execution errors.

Examples:

### Invalid Instruction

```text
UNKNOWN_OP
```

Result:

```text
Error → Interrupt / Error Handler
```

### Divide by Zero

```text
DIV 0
```

Result:

```text
Division Error
```

### Invalid Memory Access

Attempting to access an invalid address shall result in an appropriate memory error.

### Invalid System Call

An unsupported system call number shall generate an error.

---

# 25. HALT Instruction

`HALT` indicates normal termination of the currently executing program.

Flow:

```text
HALT
 ↓
CPU stops current process execution
 ↓
Process Manager marks process
TERMINATED
 ↓
Scheduler selects another process
```

The CPU itself does not decide which process runs next.

---

# 26. CPU Execution State

The simulator shall maintain a CPU state such as:

```text
CPU State
├── IDLE
├── RUNNING
├── INTERRUPTED
└── HALTED
```

The state should be available to the frontend for visualization.

---

# 27. CPU Event Generation

The CPU should produce events that can be consumed by the OS engine and frontend.

Examples:

```text
INSTRUCTION_FETCH
INSTRUCTION_EXECUTE
REGISTER_UPDATE
SYSCALL
HALT
CPU_ERROR
```

Example event:

```text
{
    "type": "INSTRUCTION_EXECUTE",
    "pid": 2,
    "instruction": "ADD 5",
    "pc": 104,
    "acc": 15
}
```

The exact event schema will be finalized during implementation.

---

# 28. CPU Simulation Timing

AIOS will use a simulated execution cycle rather than attempting to execute instructions as quickly as possible.

A configurable simulation speed may be used:

```text
Slow
Normal
Fast
```

This allows users to observe:

* Instruction execution
* Context switching
* Interrupts
* Memory access
* Scheduling decisions

The simulation speed affects visualization timing and should not change the logical correctness of the OS simulation.

---

# 29. CPU Responsibilities

The CPU Simulator is responsible for:

* Fetching instructions
* Decoding instructions
* Executing instructions
* Updating registers
* Updating flags
* Performing basic arithmetic
* Performing basic control flow
* Requesting memory access
* Triggering system-call events
* Detecting CPU-level errors
* Maintaining execution state

---

# 30. CPU Non-Responsibilities

The CPU Simulator shall **not** be responsible for:

* Choosing the next process
* Managing page tables
* Performing page replacement
* Managing process queues
* Deciding process priority
* Managing IPC
* Managing synchronization
* Managing I/O queues
* Managing AI permissions
* Performing AI scheduling

These responsibilities belong to other OS components.

This separation is important for maintaining a modular architecture.

# 32. CPU Simulation Success Criteria

The CPU component is considered complete when:

* The CPU initializes correctly.
* All required registers are maintained.
* A program can be loaded.
* Instructions can be fetched.
* Instructions can be decoded.
* Instructions can be executed.
* Arithmetic operations work correctly.
* Memory operations work through the defined memory interface.
* Branch instructions work.
* `SYSCALL` can trigger OS handling.
* `HALT` terminates the current process.
* CPU errors can be detected.
* CPU state can be saved and restored.
* Context switching can be demonstrated.
* CPU state can be displayed in the frontend.

# 34. Implementation Boundary

The CPU module should expose a simple interface to the rest of the OS.

Conceptually:

```text
CPU
├── initialize()
├── loadContext()
├── executeCycle()
├── saveContext()
├── reset()
├── getState()
└── getRegisters()
```

The exact C++ classes and method signatures will be decided during implementation.

The CPU should not expose its internal implementation unnecessarily to other modules.

# 35. Summary

The AIOS CPU / Machine Simulation provides the simulated hardware foundation required for the operating system.

The CPU:

```text
Fetches
   ↓
Decodes
   ↓
Executes
   ↓
Updates State
   ↓
Generates Events
```

The OS then uses these events to perform higher-level operations such as:

```text
Scheduling
Memory Management
Interrupt Handling
System Calls
I/O
Process Management
```

The CPU remains deliberately simple so that the project can focus on demonstrating Operating System behaviour rather than processor design.
