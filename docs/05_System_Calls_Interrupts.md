# AIOS: An AI-Powered Multiprogramming Operating System Simulator

# 5. System Calls and Interrupts

## 1. Purpose

This document defines the system call and interrupt mechanisms of AIOS.

The purpose of this module is to demonstrate how a running process requests services from the operating system and how the simulated CPU transfers control to the OS for handling.

The module covers:

* Supervisor calls
* System call numbers
* Interrupt generation
* Interrupt identification
* Context saving
* Interrupt Service Routines
* System call servicing
* Interrupt completion
* Context restoration
* Process resumption
* Timer interrupts
* Page-fault interrupts
* I/O interrupts
* Error interrupts

---

# 2. Basic Concept

A process should not directly control operating-system resources.

For example, a process cannot directly tell simulated hardware:

```text
"Give me memory."
"Read from disk."
"Send this message."
"Write output."
```

Instead, it requests the OS through a **system call**.

The general flow is:

```text
Process
   │
   │ System Call
   ▼
CPU
   │
   │ Interrupt
   ▼
Interrupt Manager
   │
   ▼
OS Service
   │
   ▼
Return Result
   │
   ▼
Process Continues
```

---

# 3. Supervisor Call

A supervisor call is a request made by a user-level process to obtain a service from the operating system.

In AIOS, a supervisor call is represented by the `SYSCALL` instruction.

Example:

```text
SYSCALL 2
```

The number identifies the requested OS service.

Conceptually:

```text
SYSCALL <service_number>
```

---

# 4. System Call Categories

AIOS shall support a small set of system calls sufficient for demonstrating OS functionality.

Initial system calls:

| Number | System Call  | Purpose               |
| -----: | ------------ | --------------------- |
|    `1` | `READ`       | Request input         |
|    `2` | `WRITE`      | Request output        |
|    `3` | `ALLOCATE`   | Request memory        |
|    `4` | `EXIT`       | Terminate process     |
|    `5` | `IPC_SEND`   | Send an IPC message   |
|    `6` | `IO_REQUEST` | Request simulated I/O |

The system call table may be extended if another subsystem requires an additional service.

---

# 5. System Call Execution

Consider:

```text
SYSCALL 2
```

The execution sequence is:

```text
1. CPU fetches SYSCALL instruction
2. CPU decodes the instruction
3. CPU identifies system call number 2
4. CPU generates a system call interrupt
5. Current process context is saved
6. Interrupt Manager identifies the interrupt
7. System Call Manager identifies service 2
8. WRITE service is executed
9. Result/status is returned
10. Process context is restored
11. Process resumes
```

---

# 6. Complete System Call Flow

```text
                 Process
                    │
                    ▼
              SYSCALL n
                    │
                    ▼
                   CPU
                    │
                    ▼
        Generate System Call Interrupt
                    │
                    ▼
          Save Process Context
                    │
                    ▼
            Interrupt Manager
                    │
                    ▼
           System Call Manager
                    │
             ┌──────┴──────┐
             │             │
             ▼             ▼
        Valid Call      Invalid Call
             │             │
             ▼             ▼
       Execute Service   Error Handler
             │             │
             └──────┬──────┘
                    ▼
            Restore Context
                    │
                    ▼
              Process Resumes
```

---

# 7. Interrupt

An interrupt is an event that causes the CPU to temporarily stop its current execution flow and transfer control to an OS handler.

In AIOS, interrupts are simulated software events.

Examples include:

```text
System Call
Timer
Page Fault
I/O Completion
CPU Error
```

---

# 8. Interrupt Types

AIOS shall initially support the following interrupt types:

```text
Interrupts
│
├── System Call Interrupt
├── Timer Interrupt
├── Page Fault Interrupt
├── I/O Interrupt
└── Error Interrupt
```

Each interrupt type has an associated handling routine.

---

# 9. Interrupt Vector

AIOS shall maintain an interrupt mapping that associates an interrupt type with its handler.

Conceptually:

```text
Interrupt Vector
│
├── SYSTEM_CALL  → System Call Handler
├── TIMER        → Timer Handler
├── PAGE_FAULT   → Page Fault Handler
├── IO_COMPLETE  → I/O Handler
└── ERROR        → Error Handler
```

When an interrupt occurs, the Interrupt Manager uses this mapping to determine which service routine should execute.

---

# 10. Interrupt Generation

An interrupt can be generated by different components.

```text
                  Interrupt Sources
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
       CPU          Memory Manager      I/O Manager
        │                │                │
        ▼                ▼                ▼
    SYSCALL          PAGE FAULT       I/O COMPLETE
        │                │                │
        └────────────────┼────────────────┘
                         ▼
                  Interrupt Manager
```

A timer mechanism can also generate periodic timer interrupts.

---

# 11. Interrupt Handling Sequence

When an interrupt occurs, AIOS follows this general sequence:

```text
1. Interrupt generated
2. Current CPU state identified
3. Current process context saved
4. Interrupt type identified
5. Appropriate handler selected
6. Interrupt Service Routine executed
7. Required OS action completed
8. Process state updated
9. Context restored or scheduler invoked
10. Execution resumes
```

---

# 12. Saving Process Context

Before servicing an interrupt, the current execution state may need to be saved.

The saved context contains:

```text
Process Context
├── PC
├── IR
├── ACC
├── MAR
├── MBR
└── FLAGS
```

Conceptually:

```text
CPU Registers
     │
     ▼
Current PCB
     │
     ▼
Saved Context
```

This allows the process to continue from the correct location later.

---

# 13. Interrupt Service Routine

An Interrupt Service Routine (ISR) is the code responsible for handling a particular interrupt.

Example:

```text
Timer Interrupt
      │
      ▼
Timer ISR
      │
      ▼
Scheduling Decision
      │
      ▼
Context Switch if Required
```

Another example:

```text
Page Fault
      │
      ▼
Page Fault ISR
      │
      ▼
Memory Manager
      │
      ▼
Load Required Page
```

---

# 14. System Call ISR

The System Call Interrupt Handler passes control to the System Call Manager.

```text
SYSCALL
   │
   ▼
System Call Interrupt
   │
   ▼
Interrupt Manager
   │
   ▼
System Call Handler
   │
   ▼
System Call Manager
   │
   ▼
Requested Service
```

---

# 15. Timer Interrupt

A timer interrupt allows the OS to regain control of the CPU periodically.

This is important for multiprogramming and preemptive scheduling.

Example:

```text
P1 Running
     │
     │ Time Quantum Expires
     ▼
Timer Interrupt
     │
     ▼
Save P1 Context
     │
     ▼
Scheduler
     │
     ▼
Select P2
     │
     ▼
Load P2 Context
     │
     ▼
P2 Running
```

This mechanism is particularly important for Round Robin scheduling.

# 16. Page Fault Interrupt

A page fault occurs when a process attempts to access a page that is not currently loaded into physical memory.

Flow:

```text
CPU
 │
 ▼
Memory Access
 │
 ▼
Page Table
 │
 ▼
Page Not Present
 │
 ▼
PAGE FAULT
 │
 ▼
Interrupt Manager
 │
 ▼
Page Fault Handler
 │
 ▼
Memory Manager
 │
 ▼
Page Replacement / Page Loading
 │
 ▼
Process Resumes
```

The detailed paging and page replacement mechanism is defined in:

```text

```

# 17. I/O Interrupt

An I/O operation may require the process to wait until the simulated device completes its operation.

Example:

```text
Process
   │
   ▼
I/O System Call
   │
   ▼
I/O Manager
   │
   ▼
Process → WAITING
   │
   ▼
Simulated Device
   │
   ▼
I/O Complete
   │
   ▼
I/O Interrupt
   │
   ▼
Interrupt Manager
   │
   ▼
Process → READY
```

The Scheduler can then select the process again.

---

# 18. Error Interrupt

Errors detected during execution may generate an error event.

Examples:

```text
Invalid Instruction
Divide by Zero
Invalid System Call
Invalid Memory Access
```

Example:

```text
DIV 0
 │
 ▼
CPU detects error
 │
 ▼
Error Interrupt
 │
 ▼
Error Manager
 │
 ▼
Process Recovery / Termination
```

The exact recovery policy is defined by the Error Manager.

---

# 19. Interrupt Priority

Multiple interrupt events may occur during simulation.

AIOS may assign priorities to interrupts.

Initial conceptual priority:

```text
High
 │
 ├── Critical Error
 ├── Page Fault
 ├── System Call
 ├── I/O Completion
 └── Timer
 │
Low
```

The exact priority ordering shall be finalized during implementation and testing.

The design should allow interrupt priorities to be changed without modifying unrelated components.

**Implementation note (2026-08-20):** the priority ordering was finalized during implementation as:

```text
High
 │
 ├── ERROR        (priority 10)
 ├── PAGE_FAULT   (priority 20)
 ├── SYSTEM_CALL  (priority 30)
 ├── IO_COMPLETE  (priority 40)
 └── TIMER        (priority 50)
 │
Low
```

Lower value = higher priority. The ordering is centralized in `InterruptManager::priorityOf()` so it can be changed in one place without modifying the dispatcher.

---

# 20. Nested Interrupts

The first implementation does not require unrestricted nested interrupts.

If an interrupt occurs while another ISR is executing, AIOS shall use a controlled policy.

Initial policy:

```text
Current ISR
     │
     ▼
New Interrupt
     │
     ▼
Queue / Defer Interrupt
     │
     ▼
Current ISR Completes
     │
     ▼
Pending Interrupt Serviced
```

This keeps the simulator simpler and more deterministic.

Nested interrupts may be added later if required.

---

# 21. Interrupt Queue

AIOS shall maintain an interrupt queue for pending interrupt events.

Example:

```text
Interrupt Queue

┌───────────────┐
│ PAGE_FAULT    │
├───────────────┤
│ IO_COMPLETE   │
├───────────────┤
│ TIMER         │
└───────────────┘
```

The Interrupt Manager processes events according to the defined interrupt policy.

---

# 22. System Call Return

After a system call completes, the process should receive a result/status.

Example:

```text
Process
   │
   │ SYSCALL ALLOCATE
   ▼
OS
   │
   │ Allocation Successful
   ▼
Return Result
   │
   ▼
Process Continues
```

For a failed request:

```text
Process
   │
   │ SYSCALL ALLOCATE
   ▼
OS
   │
   │ Insufficient Memory
   ▼
Error / Failure Status
   │
   ▼
Process Handles Result
```

---

# 23. Interrupt and Scheduling Interaction

An interrupt does not always mean that the current process must be terminated.

Depending on the interrupt, the OS may:

```text
Continue Process
Block Process
Wake Process
Reschedule
Terminate Process
Retry Operation
```

Example:

```text
Timer Interrupt
      ↓
Scheduler
      ↓
Context Switch
```

Whereas:

```text
I/O Interrupt
      ↓
Wake Waiting Process
      ↓
Scheduler
```

---

# 24. Interrupt and Context Switching

A context switch can occur because of an interrupt.

Example:

```text
P1 Running
   │
   ▼
Timer Interrupt
   │
   ▼
Save P1 Context
   │
   ▼
Scheduler
   │
   ▼
Select P2
   │
   ▼
Load P2 Context
   │
   ▼
P2 Running
```

The context switch mechanism is shared with the Process Manager and Scheduler.

# 25. System Call and AI Agent Interaction

AI agents also use OS services through the same system call mechanism.

For example:

```text
AI Research Agent
       │
       │ SYSCALL IO_REQUEST
       ▼
System Call Manager
       │
       ▼
Permission Manager
       │
       ▼
I/O Manager
       │
       ▼
Simulated Network
```

This is important because AI agents do not bypass the operating system.

They are treated as managed workloads.

# 29. Interrupt Lifecycle

Every interrupt follows a lifecycle:

```text
GENERATED
    ↓
PENDING
    ↓
SERVICING
    ↓
COMPLETED
```

An error interrupt may instead result in:

```text
GENERATED
    ↓
SERVICING
    ↓
PROCESS TERMINATED
```

The interrupt state should be recorded in the event log.

# 33. Component Responsibilities

## CPU

Responsible for:

* Detecting `SYSCALL`
* Detecting CPU errors
* Executing instructions
* Generating CPU-related events

## Interrupt Manager

Responsible for:

* Receiving interrupt events
* Identifying interrupt types
* Maintaining interrupt state
* Selecting handlers
* Managing pending interrupts

## System Call Manager

Responsible for:

* Identifying requested system calls
* Validating system calls
* Executing OS services
* Returning results

## Process Manager

Responsible for:

* Saving process context
* Updating process state
* Restoring process context
* Managing process lifecycle

## Scheduler

Responsible for:

* Selecting the next process
* Performing scheduling decisions after appropriate interrupts

## Memory Manager

Responsible for:

* Handling page faults
* Loading pages
* Managing frames
* Updating page tables

## I/O Manager

Responsible for:

* Processing I/O requests
* Generating I/O completion events

## Error Manager

Responsible for:

* Processing execution errors
* Applying recovery/termination policies

# 38. Success Criteria

The System Call and Interrupt module is considered complete when:

* A process can execute `SYSCALL`.
* The system call generates an interrupt.
* The current process context can be saved.
* The Interrupt Manager identifies the interrupt.
* The correct handler is selected.
* The requested system service executes.
* The system call result is returned.
* The process can resume.
* Timer interrupts can trigger scheduling.
* Page faults can generate interrupts.
* I/O completion can generate interrupts.
* Errors can generate appropriate events.
* Interrupt activity is recorded in the event log.
* Interrupt activity is visible in the dashboard.

# 39. Summary

The system call and interrupt mechanism provides the bridge between a running process and the operating system.

The fundamental flow is:

```text
Process
   ↓
System Call / Event
   ↓
Interrupt
   ↓
Interrupt Manager
   ↓
Appropriate OS Handler
   ↓
OS Service
   ↓
Context Restore / Scheduling
   ↓
Process Continues
```

This mechanism is essential for AIOS because it connects the CPU simulation with process management, memory management, scheduling, I/O, and AI-agent services.
